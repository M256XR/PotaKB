[Claude]
根本原因から説明します。

## HIDスクロールの仕組みと実装方法

**なぜ「3行ずつ」になるか**
HID mouse wheelは**整数値のみ**送信できます（-127〜+127）。OSが「1 = 3行スクロール」に変換するのでどんなに細かく制御しても最小単位が3行になります。

---

## 実装方法の選択肢

### ① High-Resolution Wheel（推奨）
HIDディスクリプタに `RESOLUTION_MULTIPLIER` を追加。1/120刻みで送信可能になり、OSがなめらかにスクロール。
- Windows 10 v1703+ / macOS対応
- Adafruit TinyUSBのディスクリプタを改造する必要あり
- 実装難易度：中

### ② 送信間隔を詰める（現状の延長）
1tick = 3行の制約はそのままで、「ほぼ毎ms 1tickずつ送り続ける」
→ 速度は比例させられるが最小単位は3行のまま。ユーザーの要望は満たせない

### ③ Precision Touchpad（HID Digitizer）
Windowsの精密タッチパッドとして認識させる。最もなめらかだが実装が非常に複雑

---

## 結論

「0.1行ずつ傾きに応じて変化」には **① High-Resolution Wheel** が必要です。

実装しますか？TinyUSBのHIDディスクリプタを拡張することになりますが、Adafruit BLEとUSB両方への対応が必要で、BLE側（`blehid`）はAdafruitのHIDサービスをオーバーライドする必要があるためUSBのみ対応でもよいか確認させてください。

[Claude]
**理論上は可能**ですが、現実的には難しいです。

BLE HIDもUSB HIDと同じHIDディスクリプタ形式を使うので、仕様上はResolution Multiplierを乗せられます。

ただし問題が2つあります：

**① ライブラリの制約**
Adafruitの`BLEHidAdafruit`はディスクリプタが固定されているため、カスタムディスクリプタに差し替える必要があります（`BLEHidGeneric`を使って自前実装）。

**② WindowsのBLE HIDサポートが不安定**
USB接続のHigh-Res WheelはWindows 10 v1703+で確実に動きますが、BLE経由でのHigh-Res Wheelは動作報告が少なく、OS側の対応が怪しいです。実装してみても効かない可能性があります。

---

**現実的な選択肢：**

| | USB | BLE |
|---|---|---|
| High-Res Wheel | 実装可能・動作確実 | 実装困難・OS対応不明 |
| 実装難易度 | 中 | 高 |

USBはほぼ確実に動く。BLEは博打になります。

**どうしますか？**
- USBのみHigh-Res対応（BLEは現状維持）でよければ実装できます
- BLEも試したければやってみますが動かない可能性込みになります

**Root cause**: The Bluefruit52 library stores bond files as `/adafruit/bond_prph/<PEER_MAC>`. When using the same Windows PC to test all 3 slots, every pairing overwrites the same file (same Windows MAC). So when cycling back to cyan, the nRF52 loads the **wrong LTK** (from whichever slot was paired last) → encryption fails → connection succeeds at link layer but HID is inaccessible because the characteristics require encryption.

**Fix**: Per-slot bond directories:
- Slot 0 (blue): `/adafruit/bond_prph/` (original, unchanged)
- Slot 1 (cyan): `/adafruit/bond_prph_1/`
- Slot 2 (magenta): `/adafruit/bond_prph_2/`

`startAdvertising(btSlot)` now calls `bond_set_slot(btSlot)` first, which switches the active directory. Every bond operation (save/load keys, save/load CCCD) then uses the slot-specific directory, so each slot's pairing info is completely isolated.

**Changes made**:
1. `bonding.cpp` — added `bond_set_slot()`, `g_bond_dir_prph` variable, updated `get_fname`, `bond_init`, `bond_clear_prph`, `bond_clear_all`, and the resolvable address scan
