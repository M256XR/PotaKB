## 発見したバグ・問題点

### 🔴 重大なバグ

**1. `KC_TRNS` と `KC_NO` が同じ値 (0x000)**
```c
// keymap.h
#define KC_NO   0x000
#define KC_TRNS 0x000  // ← 同じ！
```
`processAllInputs()` で「値が0ならレイヤー0に透過」しているため、Lowerレイヤーで `KC_NO` としたキーが全部レイヤー0のキーに透過してしまいます。例えば Lower+Q は何もしないはずが 'Q' が入力されます。

**2. バッファサイズの不一致（潜在的な配列外アクセス）**
```c
// コンパイル時サイズ (= 2)
int xReadings[SMOOTHING_SAMPLES], yReadings[SMOOTHING_SAMPLES];

// 実行時にConfigから読む
readIndex = (readIndex + 1) % currentConfig.smoothing_samples;
int xAvg = xTotal / currentConfig.smoothing_samples;
```
設定で `smoothing_samples` が `SMOOTHING_SAMPLES(2)` より大きい値になると配列外アクセスです。

### 🟡 中程度の問題

**3. BLE Advertising に HID サービスが含まれていない**
```c
// initBluetooth() より
Bluefruit.Advertising.addService(keymapService);   // keymapだけ
Bluefruit.ScanResponse.addService(blehid);         // HIDはScanResponseのみ
Bluefruit.ScanResponse.addAppearance(BLE_APPEARANCE_HID_KEYBOARD);  // これも
```
Advertising パケットに HID サービスと Appearance がないため、ScanResponse を要求しないホストで認識されない可能性があります。

**4. `applyConfig()` が空関数**
```c
void applyConfig() { /* 設定はcurrentConfig構造体を直接参照するため、この関数は実質不要 */ }
```
`NVIC_SystemReset()` で再起動しているので実害はないですが、将来混乱の原因になります。

### 🔵 マイナーな問題

**5. Bluetooth補正が定数5倍のハードコード**
```c
speed *= 5.0f;  // Bluetoothは1ms→3ms間隔なのに5倍？（本来3倍が自然）
```

## 現行コードの問題特定

**スティック逆方向バグの原因：**
```cpp
// X/Yピンが逆に読まれている
xReadings[readIndex] = analogRead(STICK_Y_PIN);  // ← 物理Yをロジック用Xに
yReadings[readIndex] = analogRead(STICK_X_PIN);

// さらにY軸だけ符号が逆
int xDiff = xAvg - stick_center_x;
int yDiff = stick_center_y - yAvg;  // ← Xと逆算式
```

**ガクガクの原因：**
```cpp
// 「BLEは遅いから5倍」というハードコード補正
if (currentMode == MODE_BLUETOOTH) {
    speed *= 5.0f;  // ← 実際の経過時間を無視
}
```
送信間隔が一定でないのに定数倍しているため、タイミングのブレがそのまま動きのブレになる。

**正しい方法は `velocity × deltaTime`：** 実際に何ms経ったか計算してその分だけ動かせばBLEでもUSBでも同じ動きになる。

## nRF5 SDK vs Arduino+Bluefruit

**nRF5 SDKで得られるもの：**
- バイナリサイズが少し小さい
- 電源管理の細かい制御ができる
- SoftDevice（BLEスタック）への直アクセス

**でも実際は：**

Adafruit の nRF52 Arduino core は**内部で nRF5 SDK + SoftDevice をそのまま使ってる**ただのラッパーです。BLEスタックの性能は同じ。

今回の問題（ガクガク・逆方向）はSDKの問題じゃなくて**ソフトウェアのバグ**なので、nRF5 SDKで書いても同じバグは起きます。

**nRF5 SDKのデメリット：**
- USB HIDを自前で実装しないといけない（めちゃ面倒）
- BLE HIDのデスクリプタも手書き
- ビルド環境の構築が複雑（Segger Embedded Studio か GCC + Makefile）
- コード量が3〜5倍になる

---

**結論：** このプロジェクトのボトルネックはI2Cスキャン速度とBLE接続間隔で、どちらもSDK変えても変わらないので Arduino+Bluefruit で十分です。

ZMK（Zephyr RTOS）はまさに nRF52840 向けの本格的なキーボードFWですが、アナログスティックとカスタムI2Oエクスパンダの組み合わせがサポート外なので結局カスタムドライバを書くことになって旨みが消えます。
